# 第 04 讲代码实战：工具边界——截断、超时、路径三道防线

学城第 04 讲的重点不是“给工具补几个 `if`”，而是一个很重要的 Agent 工程原则：

> **模型产生的工具参数不是可信输入。工具除了完成正常功能，还必须保证异常输入不会拖垮上下文、卡死主循环或越界访问。**

在本项目里，第 04 讲主要对应以下文件：

| 文件 | 对应能力 |
|---|---|
| `src/tools/read-file.js` | 读取文件、8000 个 JavaScript 字符截断、已有文件路径校验 |
| `src/tools/bash.js` | Shell 命令 30 秒超时、stdout/stderr 合并输出、8000 UTF-8 字节头尾截断 |
| `src/tools/path-utils.js` | 工作区词法路径边界、符号链接真实路径二次校验 |
| `src/tools/write-file.js` | 写文件时的工作区词法路径校验与自动建目录 |
| `src/tools/edit-file.js` | 编辑文件前的词法路径与符号链接校验 |
| `src/tools/registry.js` | 将工具抛出的异常统一转成 `ToolResult`，而不是让 Agent 引擎崩溃 |
| `src/context/recovery.js` | 对部分错误附加模型可执行的“救援指南” |

---

## 1. 先建立整体图：三道防线分别在防什么

模型可能发出下面几种看似合理、实际危险的调用：

```js
// 输出过大
{ name: 'read_file', arguments: { path: 'logs/access.log' } }

// 永不结束
{ name: 'bash', arguments: { command: 'npm run dev' } }

// 越界路径
{ name: 'write_file', arguments: { path: '../../outside.txt', content: '...' } }
```

如果工具“照单全收”，问题分别是：

| 风险 | 直接后果 | 本项目的处理 |
|---|---|---|
| 文件/命令输出太大 | 巨量内容写入 Session，下一次模型调用上下文超限且持续烧 Token | 截断输出 |
| 命令长期运行 | `await bash.execute()` 永远不返回，整轮 Agent 卡住 | 30 秒后强制终止 |
| 路径逃逸工作区 | 误读、误改工作区外的文件 | 在文件工具入口拒绝越界路径 |

在一次正常工具调用中，边界处理和主循环的关系如下：

```text
模型 ToolCall
    ↓
AgentEngine 调用 Registry.execute(call)
    ↓
ReadFileTool / WriteFileTool / EditFileTool / BashTool.execute(args)
    ├─ 文件工具：路径守卫
    ├─ read_file：内容长度守卫
    └─ bash：执行时间、输出字节数守卫
    ↓
成功字符串 或 throw Error
    ↓
Registry 捕获异常，统一返回 ToolResult(isError: true)
    ↓
Engine 将结果写回 Session，模型下一轮根据结果调整行为
```

关键点：**工具失败是可预期业务结果，不应该变成整个 Node.js 进程崩溃。**

## 2. 第一层：`read_file` 的 8000“字符”截断

对应 `src/tools/read-file.js`：

```js
const MAX_LEN = 8000;

async execute(args) {
  try {
    const fullPath = resolveWorkspacePath(this.workDir, args.path);
    const safePath = assertExistingPathInsideWorkspace(this.workDir, fullPath);
    const content = fs.readFileSync(safePath, 'utf-8');

    if (content.length > MAX_LEN) {
      return content.slice(0, MAX_LEN) +
        `\n\n...[由于内容过长，已被系统截断至前 ${MAX_LEN} 个字符]...`;
    }
    return content;
  } catch (err) {
    throw new Error(`打开文件失败: ${err.message}`);
  }
}
```

### 2.1 为什么不能完整返回文件内容

`read_file` 的返回值不会只显示在终端，它会经过 `Registry → Engine → Session`，成为模型下一轮输入的一部分。

假设 `access.log` 有 10MB：

```text
read_file 返回 10MB
  → Engine 把 10MB 写入 Session
  → 下一轮 Provider.generate(...) 带上这 10MB
  → 请求可能触发上下文长度限制，且输入 Token 成本明显上升
```

所以限制的是**进入 Agent 上下文的观察结果**，而不是为了让 `fs.readFileSync` 少读一点。当前实现仍会把整个文件读入 Node.js 内存，然后再截断返回；对于超大文件，这仍可能造成进程内存压力。更进一步的生产级优化是流式读取前 N 个字节，而不是全量读取后 `slice`。

### 2.2 为什么是 `content.length`，不是字节数

`content` 是 JavaScript 字符串，`content.length` 统计的是 UTF-16 代码单元。它不是：

- UTF-8 字节数；
- Unicode 用户感知字符数（例如部分 emoji 可能占两个代码单元）；
- Token 数。

因此，学城文档所说的“8000 字符”，在代码中严格说是 **8000 个 JavaScript 字符串长度单位**。

### 2.3 为什么只保留开头

代码使用：

```js
content.slice(0, MAX_LEN)
```

即只保留前 8000 个字符。这适合读取源码：文件开头通常包含 import、类型定义、核心入口与注释，能帮助模型快速定位结构。

代价是：报错信息或关键内容若位于日志末尾，模型看不到。此时模型应改用 `bash` 的 `tail`、`grep` 等更有针对性的命令，而不是继续全量读日志。

### 2.4 截断标记为何重要

返回值末尾明确包含：

```text
...[由于内容过长，已被系统截断至前 8000 个字符]...
```

这不是装饰文本。它告诉模型“这不是完整文件”，避免模型把缺失的尾部误判为不存在，从而引导模型继续按范围、关键字或尾部查询。

## 3. 第二层：`bash` 的 30 秒超时

对应 `src/tools/bash.js`：

```js
const TIMEOUT_MS = 30_000;

const child = spawn('sh', ['-c', command], {
  cwd: this.workDir,
  env: process.env,
});

const timer = setTimeout(() => {
  if (settled) return;
  settled = true;
  child.kill('SIGKILL');
  reject(new Error(
    formatOutput(stdout, stderr) +
      `\n[⚠️ 命令超过 ${this.timeoutMs}ms 未结束，已被强制终止]`
  ));
}, this.timeoutMs);
```

### 3.1 为什么 `npm run dev` 会卡住 Agent

AgentEngine 在一轮中等待工具 Promise 完成：

```js
const result = await this.registry.execute(call);
```

而开发服务器、watch 命令或死循环命令不会自行退出。没有超时，`BashTool.execute()` 的 Promise 就一直 pending，当前工具调用、当前 Turn、主循环都会停住。

`setTimeout` 相当于给命令设置最后期限：30 秒仍未结束，就执行 `child.kill('SIGKILL')`，随后用 `reject(...)` 把控制权交回 Registry。

### 3.2 为什么使用 `spawn`，不使用 `execSync`

`execSync` 会阻塞 Node.js 主线程。虽然它也有超时选项，但项目需要：

1. 实时监听并累积 `stdout` 与 `stderr`；
2. 用自己的计时器处理超时；
3. 在异步 Agent 主循环内返回 Promise；
4. 将完整诊断信息返回模型。

因此使用：

```js
spawn('sh', ['-c', command], { cwd: this.workDir, env: process.env })
```

`sh -c` 使输入按 shell 语法解析；这也是为什么 `BashTool` 明确不是安全沙箱，危险命令需要 Registry 上的审批 middleware 进一步控制。

### 3.3 `settled`：避免“超时”和“正常退出”重复结算

代码里有：

```js
let settled = false;
```

它保护三个异步事件源：

- `setTimeout`：超时；
- `child.on('close')`：子进程正常退出或非零退出；
- `child.on('error')`：进程创建失败等异常。

例如命令恰好在第 30 秒退出，`close` 和 timeout 回调可能非常接近。如果没有 `settled`，就可能既 `resolve` 又 `reject`，或超时后再次处理退出事件。当前逻辑保证第一个完成结算的事件获胜：

```js
if (settled) return;
settled = true;
```

并在正常 close 路径清除定时器：

```js
clearTimeout(timer);
```

### 3.4 超时并不等于“命令没留下副作用”

超时只能让 Harness 停止等待并尝试杀死直接创建的子进程，不保证：

- shell 派生的所有孙进程都被清理；
- 命令此前的文件写入、网络请求、数据库操作被回滚；
- `SIGKILL` 在所有平台上的语义完全相同。

所以超时是**可用性防线**，不是事务回滚机制，更不是权限隔离。

## 4. `bash` 还有一层输出截断：8000“UTF-8 字节”保留头尾

和 `read_file` 不同，Shell 命令的输出更常见“开头是进度、末尾才是错误”。因此 `bash` 不只保留开头，而是保留头尾。

```js
function formatOutput(stdout, stderr) {
  let text = '';
  if (stdout.length > 0) {
    text += stdout.toString('utf8');
  }
  if (stderr.length > 0) {
    if (text) text += '\n';
    text += `[stderr]\n${stderr.toString('utf8')}`;
  }

  const encoded = Buffer.from(text, 'utf8');
  if (encoded.length > MAX_OUTPUT_BYTES) {
    const head = encoded.subarray(0, 4000).toString('utf8');
    const tail = encoded.subarray(encoded.length - 4000).toString('utf8');
    const skipped = encoded.length - 8000;
    text = `${head}\n\n...[输出超过 8000 字节，中间 ${skipped} 字节已被截断]...\n\n${tail}`;
  }
  return text;
}
```

### 4.1 先合并 stdout 和 stderr，再截断

这段顺序有意义：

```js
stdout + '\n' + '[stderr]\n' + stderr
```

然后才按总长度截断。模型最终得到一份统一诊断文本，并能通过 `[stderr]` 知道哪部分来自标准错误。

命令非零退出时，代码仍带上输出：

```js
if (code !== 0) {
  reject(new Error(`${out}\n[退出码: ${code}]`));
}
```

因此模型不会只收到“失败了”，还会拿到 stdout、stderr 与退出码，具备修复命令的证据。

### 4.2 必须分清两个 8000

| 工具 | 上限 | 单位 | 截断方式 |
|---|---:|---|---|
| `ReadFileTool` | 8000 | JavaScript 字符串长度单位 | 前 8000 |
| `BashTool` | 8000 | UTF-8 字节 | 前 4000 字节 + 后 4000 字节 |

为什么 Bash 用字节？`child.stdout` / `child.stderr` 回调给出的原始数据就是 `Buffer`，按字节累积和限制更贴近实际 I/O 数据大小。

### 4.3 一个实现细节：多字节字符边界

代码将字节片段直接 `toString('utf8')`：

```js
encoded.subarray(0, 4000).toString('utf8')
```

如果第 4000 个字节刚好切在一个中文字符或 emoji 的中间，显示时可能出现替换字符 `�`。注释已明确说明这是当前实现的可接受代价。

更严格的方案是找到合法 UTF-8 边界后再切，但会增加实现复杂度；教学项目以“保护上下文长度”为优先目标。

## 5. 第三层：文件路径必须落在 `workDir` 内

路径防线集中在 `src/tools/path-utils.js`，文件工具不会直接相信模型给的 `args.path`。

```js
export function resolveWorkspacePath(workDir, requestedPath) {
  if (typeof requestedPath !== 'string' || requestedPath.length === 0) {
    throw new Error('文件路径不能为空');
  }

  const root = path.resolve(workDir);
  const target = path.resolve(root, requestedPath);
  const relative = path.relative(root, target);

  if (isOutside(relative)) {
    throw new Error(`路径位于工作区外，拒绝访问: ${requestedPath}`);
  }
  return target;
}
```

### 5.1 `path.resolve`：先把相对路径标准化

假设：

```text
workDir = /Users/me/project
requestedPath = src/../README.md
```

标准化后：

```text
root   = /Users/me/project
target = /Users/me/project/README.md
```

这是合法的，因为最终位置仍在工作区内。

但若模型传：

```text
requestedPath = ../../.ssh/id_rsa
```

则：

```text
target = /Users/.ssh/id_rsa
relative = ../../.ssh/id_rsa
```

`isOutside(relative)` 返回 true，工具抛出越界错误。

### 5.2 `isOutside` 判断了哪些情况

```js
function isOutside(relativePath) {
  return (
    relativePath === '..' ||
    relativePath.startsWith(`..${path.sep}`) ||
    path.isAbsolute(relativePath)
  );
}
```

它防的是：

- 目标正好是工作区父目录：`..`；
- 目标在工作区父目录的更深位置：`../secret.txt`；
- 计算出的相对结果仍异常地为绝对路径。

注意：不是靠简单判断字符串里是否含 `..`。`src/../README.md` 含有 `..`，但它最终仍在工作区内，应被允许。正确做法是先 resolve，再比较最终路径关系。

## 6. 仅防 `../` 不够：符号链接绕过与二次校验

以下路径在字符串层面看似安全：

```text
project/
  fake-passwd -> /etc/passwd
```

模型调用：

```js
{ path: 'fake-passwd' }
```

`fake-passwd` 位于 `project` 中，第一层的 `resolveWorkspacePath` 会放行；但真正读取时，操作系统会沿符号链接访问 `/etc/passwd`。

因此已有文件还要调用：

```js
export function assertExistingPathInsideWorkspace(workDir, target) {
  const rootReal = fs.realpathSync(path.resolve(workDir));
  const targetReal = fs.realpathSync(target);
  const relative = path.relative(rootReal, targetReal);

  if (isOutside(relative)) {
    throw new Error('目标通过符号链接指向工作区外，拒绝访问');
  }
  return targetReal;
}
```

`realpathSync` 会解析所有符号链接，得到真实路径；再重新做一次相对路径检查。

实际使用位置：

```js
// read-file.js
const fullPath = resolveWorkspacePath(this.workDir, args.path);
const safePath = assertExistingPathInsideWorkspace(this.workDir, fullPath);
const content = fs.readFileSync(safePath, 'utf-8');

// edit-file.js
fullPath = resolveWorkspacePath(this.workDir, relPath);
fullPath = assertExistingPathInsideWorkspace(this.workDir, fullPath);
originalContent = await fs.readFile(fullPath, 'utf8');
```

这就是“词法路径检查 + 真实路径检查”的两层含义。

## 7. `write_file` 为什么只做第一层路径检查

对应 `src/tools/write-file.js`：

```js
async execute(args) {
  try {
    const fullPath = resolveWorkspacePath(this.workDir, args.path);
    fs.mkdirSync(path.dirname(fullPath), { recursive: true });
    fs.writeFileSync(fullPath, args.content, 'utf-8');
    return `成功将内容写入到文件: ${args.path}`;
  } catch (err) {
    throw new Error(`写入文件失败: ${err.message}`);
  }
}
```

这里没有调用 `assertExistingPathInsideWorkspace`，原因是写入目标或父目录可能尚不存在，而 `realpathSync` 只能解析已有路径。

这也意味着当前实现的保护力度要准确理解：

- **保证：** 模型传 `../../outside.txt`、`/etc/passwd` 等词法越界路径会被拒绝；
- **不保证：** 若工作区内部已经存在指向外部的符号链接目录，向该目录下新建文件的情况能被完全阻止。

例如工作区内有 `out-link -> /tmp/outside`，调用 `write_file({ path: 'out-link/a.txt' })` 时，词法路径仍在工作区，`mkdirSync` / `writeFileSync` 可能跟随链接写到外部。

这是当前教学实现的一个安全边界。生产级实现应在创建前逐级检查父目录真实路径，或使用更底层、避免跟随链接的文件系统 API 与容器沙箱。

## 8. 路径边界不等于 Bash 沙箱

一个容易误解的点：`BashTool` 只是把默认工作目录设置成 `workDir`：

```js
const child = spawn('sh', ['-c', command], {
  cwd: this.workDir,
  env: process.env,
});
```

`cwd` 的含义是：命令从工作区开始执行，所以 `ls`、`npm test`、`cat src/index.js` 默认针对当前项目。

但它不等于把进程锁在工作区。模型仍可能执行：

```sh
cat /etc/passwd
rm -rf /tmp/example
cd .. && ls
```

是否能成功取决于运行该 Node.js 进程的操作系统权限。因此：

| 能力 | 本项目是否提供 |
|---|---|
| `read_file` / `write_file` / `edit_file` 的工作区路径守卫 | 是 |
| Bash 命令默认从工作区启动 | 是 |
| Bash 访问工作区外的 OS 级隔离 | 否 |
| 容器、用户权限、seccomp 等真正进程沙箱 | 否 |

这也是为什么项目同时在 `Registry` 层提供危险操作的审批 middleware：文件工具路径守卫、审批、人机确认和 OS/容器隔离是不同层面的防御，不能相互替代。

## 9. 工具报错如何回到模型，而不是炸掉整个循环

工具内部会 `throw new Error(...)`，例如超时：

```js
reject(new Error(
  formatOutput(stdout, stderr) +
  `\n[⚠️ 命令超过 ${this.timeoutMs}ms 未结束，已被强制终止]`
));
```

`Registry.execute()` 统一捕获：

```js
try {
  const output = await tool.execute(call.arguments);
  return new ToolResult({
    toolCallId: call.id,
    output,
    isError: false,
  });
} catch (err) {
  return new ToolResult({
    toolCallId: call.id,
    output: `Error executing ${call.name}: ${err.message}`,
    isError: true,
  });
}
```

这使得错误变成结构化的 Agent 观察结果。随后 Engine 对 `isError` 结果调用 `RecoveryManager`：

```js
if (result.isError) {
  finalOutput = this.recovery.analyzeAndInject(call.name, result.output);
}
```

针对 Bash 的超时，`recovery.js` 会额外提示：

```text
该命令执行被超时强杀。如果它是一个常驻服务（如 server 或 watch），
请将其转入后台执行（例如使用 nohup ... &），不要阻塞主线程。
```

所以“超时”不是一个没有上下文的失败，而是在告诉模型：这个任务需要改变执行策略，例如运行一次性测试、缩小命令范围，或将常驻服务转入后台。

## 10. 把三道防线串成一次真实调用

假设模型希望看一段很长的日志：

```js
new ToolCall({
  id: 'call_log_01',
  name: 'read_file',
  arguments: { path: 'logs/access.log' },
});
```

执行过程：

```text
1. resolveWorkspacePath(workDir, 'logs/access.log')
   └─ 校验标准化后的路径仍在工作区

2. assertExistingPathInsideWorkspace(...)
   └─ 解析符号链接后，确认真实文件仍在工作区

3. fs.readFileSync(...)
   └─ 读取文件

4. content.length > 8000 ?
   ├─ 否：返回完整内容
   └─ 是：仅返回前 8000 个 JavaScript 字符 + 截断说明

5. Registry 返回 ToolResult
   └─ Engine 写入 Session，模型据此继续分析
```

再假设模型执行开发服务器：

```js
new ToolCall({
  id: 'call_dev_01',
  name: 'bash',
  arguments: { command: 'npm run dev' },
});
```

执行过程：

```text
1. spawn('sh', ['-c', 'npm run dev'], { cwd: workDir })
2. 开始收集 stdout/stderr
3. 同时启动 30 秒计时器
4. 30 秒内未退出
   └─ SIGKILL → reject(超时错误 + 当前已收集输出)
5. Registry 转成 ToolResult(isError: true)
6. RecoveryManager 为模型附加“常驻服务请后台执行”的建议
```

## 11. 这讲最该记住的结论

1. **截断保护的是模型上下文，不是展示界面。** 工具输出会进入 Session 并参与下一轮推理，必须控制体积。
2. **超时保护的是 Agent 调度能力。** 只要一个工具 Promise 永远不结束，主循环就无法继续。
3. **路径校验要先标准化再比较。** 不能只用字符串搜索 `..`。
4. **已有文件要防符号链接绕过。** 词法路径在工作区内，不代表真实目标也在。
5. **路径守卫不是 Bash 沙箱。** `cwd` 只是默认目录；真正隔离仍需要审批、最小权限、容器或操作系统机制。
6. **失败应回灌模型。** Tool 的边界错误通过 `ToolResult` 和恢复提示转成下一轮决策依据，而不是直接结束 Agent 进程。

第 04 讲表面上是 8000、30 秒、路径判断几个简单常量与 API；本质上是在建立一条底线：即使模型给出了过大、过慢、越界的参数，Harness 也必须保持可控、可诊断、可恢复。
