# 06｜本地执行调度器：队列、配额与取消治理

## 1. 为什么要从 `spawn` 升级为调度器

改造前，`BashTool` 的路径很直接：

```text
模型 ToolCall(bash)
  → Registry.execute
  → BashTool.execute
  → spawn('sh', ['-c', command])
```

这种实现适合低频教学演示，但多个 Agent、多个 Tool Call 同时出现时，每个调用都会立即创建子进程。问题不在 `spawn` 本身，而在于没有“准入层”：

- 不能限制全局同时运行多少条命令；
- 同一个 Session 或 Worker 可以占满全部执行槽位；
- 没有排队、排队超时和取消；
- 只能看到单条命令的结果，无法回答“队列是否积压”“平均等待多久”“超时/取消比例是多少”。

第一期的目标不是实现 Docker、cgroup 或分布式集群，而是先把本地执行路径改造成可治理的单进程调度系统：

```text
ToolCall(bash)
  → ExecutionScheduler.submit
  → PENDING 队列
  → 并发 / Session / Agent 配额准入
  → RUNNING：BashTool.spawn
  → 终态归档 + 指标 + Trace Event
```

这为第二期替换 Docker 执行后端、第三期增加容器池和资源准入提供了稳定边界。

## 2. 改造范围与非目标

### 本期实现

1. **任务状态机**：`PENDING → RUNNING → SUCCEEDED / FAILED / CANCELLED / QUEUE_TIMEOUT`。
2. **FIFO 队列与全局并发上限**：避免无限制创建子进程。
3. **双维度配额**：按 `sessionId`、`agentId` 限制同时运行的任务数，避免单个会话或 Worker 独占资源。
4. **排队超时**：任务长时间得不到执行槽位时主动失败，而不是无期限等待。
5. **取消**：排队任务直接移除；运行中任务通过 `AbortSignal` 通知 `BashTool` 杀掉子进程。
6. **指标与链路事件**：记录提交、启动、成功、失败、取消、排队超时、累计等待/运行时长；并写入现有 JSON Trace。
7. **测试**：覆盖全局并发、Session 配额、排队超时、取消及 Bash 接入。

### 本期不做

- 不做 Container / microVM / fullVM；`BashTool` 仍是本机 `sh -c`，不是安全沙箱。
- 不做 CPU、内存、PID 等 OS 级配额；本期的“配额”是**执行槽位数量**，不是 cgroup 资源限制。
- 不做跨进程、跨机器调度，也没有持久化队列；进程重启后内存队列会消失。
- 不做自动重试。命令是否重试仍由 Agent 基于 ToolResult 决策；原样失败重试由 Reminder 防护。

## 3. 新增模块与职责

```text
src/execution/
  ├── scheduler.js          任务状态机、队列、配额、取消、指标
  ├── context.js            AsyncLocalStorage 保存当前 session / agent 身份
  └── default-scheduler.js  读取环境变量并创建 CLI 共享调度器
```

### 3.1 `ExecutionScheduler`

`ExecutionScheduler` 是本期核心。它不关心命令是什么，也不关心执行后端是 Shell 还是 Docker；它只要求调用方提供：

```js
scheduler.submit({
  sessionId,
  agentId,
  label: 'bash',
  run: (signal) => executeSomething(signal),
});
```

`submit` 返回 Job：

```text
Job
  id             UUID
  sessionId      所属主任务或子任务
  agentId        root / reviewer / tester 等角色
  status         PENDING、RUNNING 或终态
  promise        调用方等待的最终结果
  controller     用于取消运行任务的 AbortController
  queueWaitMs    排队等待时长
  runMs          实际执行时长
```

这一层把“任务治理”从具体的 Shell 代码中拿出来。未来加 `DockerBackend` 时，仍然使用相同的 `submit` 协议，只需替换 `run(signal)` 的实现。

### 3.2 `execution/context.js`

`BashTool.execute()` 只知道模型传来的 `command`，天然不知道这个命令属于哪个 Session、哪个 Agent。为了不在每一层函数都手动新增 `sessionId` / `agentId` 参数，使用第二个 `AsyncLocalStorage` 保存执行身份：

```text
AgentEngine.run(session)
  → runWithExecutionContext({ sessionId, agentId: 'root' })
  → Registry.execute
  → BashTool.execute
  → getExecutionContext()
```

主 Agent 的执行上下文是：

```js
{ sessionId: session.id, agentId: 'root' }
```

子 Agent 执行时则使用：

```js
{ sessionId: threadId, agentId: agent.id }
```

这里子 Agent 把 Thread 当作调度维度中的“会话”：它代表一段独立、可续接的子任务上下文。这样同一 Worker 的不同 Thread 互不影响，而同一 Thread 的任务又能受到该维度的并发限制。

> 注意：Trace 的 `AsyncLocalStorage` 和执行身份的 `AsyncLocalStorage` 互不冲突。前者负责 Span 父子关系，后者负责资源配额归属。

### 3.3 默认调度器

`default-scheduler.js` 提供进程级共享的 `defaultExecutionScheduler`。它读取以下环境变量：

| 变量 | 默认值 | 作用 |
|---|---:|---|
| `TINY_HARNESS_MAX_EXECUTIONS` | 4 | 全局同时运行任务数 |
| `TINY_HARNESS_MAX_EXECUTIONS_PER_SESSION` | 2 | 单 Session / Thread 最大同时运行数 |
| `TINY_HARNESS_MAX_EXECUTIONS_PER_AGENT` | 2 | 单 Agent 角色最大同时运行数 |
| `TINY_HARNESS_MAX_QUEUE_WAIT_MS` | 30000 | 最大排队时长（毫秒） |

例如：

```bash
TINY_HARNESS_MAX_EXECUTIONS=8 \
TINY_HARNESS_MAX_EXECUTIONS_PER_SESSION=2 \
node src/index.js --provider openai --prompt "运行测试"
```

测试或嵌入场景可以在构造 `BashTool` 时传入专属 Scheduler，避免共享全局状态：

```js
const scheduler = new ExecutionScheduler({ maxConcurrent: 1 });
const bash = new BashTool(workDir, { scheduler });
```

## 4. 状态机：每个任务会经历什么

```text
submit
  ↓
PENDING ── cancel ───────────────→ CANCELLED
  │
  ├── 等待超过 maxQueueWaitMs ───→ QUEUE_TIMEOUT
  │
  └── 通过全局 + Session + Agent 配额
                ↓
             RUNNING
       ┌────────┼────────┐
       ↓        ↓        ↓
SUCCEEDED   FAILED   CANCELLED
                  （运行中调用 cancel）
```

- `PENDING`：已提交到队列，但尚未获得执行槽位。
- `RUNNING`：Scheduler 已占用全局及两个维度的配额，开始调用 `run(signal)`。
- `SUCCEEDED`：执行后端成功返回。
- `FAILED`：后端抛错，例如 Shell 非 0 退出、工具自身超时。
- `CANCELLED`：调用 `cancel(jobId)`；运行中任务接收 `AbortSignal` 后被终止。
- `QUEUE_TIMEOUT`：排队时间超过上限。它与 Shell 的命令运行超时不同：前者还没开始执行，后者已经开始执行但运行太久。

所有终态只会结算一次。`_finish` 会清除排队定时器、释放运行配额、更新指标、resolve/reject 调用方 Promise，并再次触发 `_drain()` 尝试启动后续任务。

## 5. 队列与配额：为什么不是简单的 `Promise.all`

Engine 仍然会对同一轮独立 Tool Call 使用 `Promise.all`，原因是模型可能同时请求多个独立工具；但它们不会再绕过治理层直接 `spawn`。

```text
Promise.all
  ├── bash A → submit → PENDING
  ├── bash B → submit → PENDING
  └── bash C → submit → PENDING

Scheduler 根据配额决定谁先 RUNNING，其余保持 PENDING。
```

`_drain()` 每次从队列中找第一个满足以下条件的任务：

```text
running < maxConcurrent
AND runningBySession[sessionId] < maxPerSession
AND runningByAgent[agentId] < maxPerAgent
```

满足则启动；不满足则跳过当前任务继续扫描，避免队头任务因为自身配额满而阻塞后面属于其他 Session/Agent、实际可以运行的任务。这是一个简化的“跳过式 FIFO”：尽量保持先提交先执行，同时避免明显的队头阻塞。

示例：

```text
全局上限 = 2，单 Session 上限 = 1

队列：S1-A、S1-B、S2-A

启动 S1-A 后，S1-B 因 S1 已满不能启动；
但 S2-A 可启动，因此它不会被 S1-B 阻塞。
```

本期没有优先级队列和公平性 aging；若某个维度长期满载，后续可以增加优先级、权重或最大排队配额。

## 6. BashTool 如何接入

改造后 `BashTool.execute()` 不直接创建进程，而是：

```text
1. getExecutionContext() 取得 sessionId / agentId
2. scheduler.submit(...) 创建 Job
3. Scheduler 允许后调用 BashTool._runProcess(command, signal)
4. BashTool 使用 spawn 执行真实命令
5. 结果通过 Job.promise 返回 Registry
```

其中职责划分如下：

| 模块 | 职责 |
|---|---|
| `ExecutionScheduler` | 排队、并发配额、排队超时、取消状态、指标 |
| `BashTool._runProcess` | `spawn`、stdout/stderr 收集、命令运行超时、`SIGKILL`、输出截断 |
| `Registry` | 工具名称路由、Middleware 审批、将异常转为 `ToolResult` |
| `AgentEngine` | 同轮工具并发、Recovery、Reminder、会话写回 |

命令执行超时仍属于 `BashTool`：例如命令已经运行 30 秒，它需要杀掉子进程。排队超时属于 Scheduler：例如执行槽位全满，命令等了 30 秒还没开始，就不应再启动。

运行中的取消通过 `AbortSignal` 打通：

```text
scheduler.cancel(jobId)
  → AbortController.abort(reason)
  → BashTool 的 abort listener
  → child.kill('SIGKILL')
  → Job 标记 CANCELLED
```

## 7. 指标与 Trace

### 7.1 进程内指标

`getSnapshot()` 返回：

```js
{
  limits: { maxConcurrent, maxPerSession, maxPerAgent, maxQueueWaitMs },
  queued,
  running,
  metrics: {
    submitted,
    started,
    succeeded,
    failed,
    cancelled,
    queueTimedOut,
    totalQueueWaitMs,
    totalRunMs,
    averageQueueWaitMs,
    averageRunMs,
  },
}
```

它是第一期的进程内实时快照。因为没有 Metrics Server，进程结束后指标不会持久化；后续服务化时可以接 Prometheus / OpenTelemetry Metrics。

### 7.2 Trace Event

现有 Trace 主要存 Span 树。本期为 `Span` 增加 `events`，调度器在当前异步 Trace 上记录：

```text
execution.queued
execution.started
execution.finished
```

每个事件包含 `jobId`、Session/Agent、状态、排队耗时和运行耗时等信息。这样在 `.tiny-harness/traces/*.json` 中不仅能看到“bash 工具耗时”，还能定位它是在排队慢还是执行慢。

`BashTool` 还将 `executionJobId`、`executionSessionId`、`executionAgentId` 写入当前工具 Span，便于将 Tool 调用和 Scheduler Job 对齐。

## 8. 测试覆盖

新增 `test/execution-scheduler.test.js`，覆盖：

1. **全局并发限制**：`maxConcurrent = 1` 时两个任务的同时运行峰值必须为 1，并验证第二个任务产生排队时长。
2. **Session 配额**：同一 Session 的第二个任务被限制，但另一 Session 的任务可以利用空闲槽位立即执行。
3. **排队超时**：执行槽位一直被占用时，等待任务进入 `QUEUE_TIMEOUT`。
4. **运行中取消**：Scheduler 发送 `AbortSignal`，任务以 `CANCELLED` 终态结束。
5. **Bash 集成**：通过 Registry 调用 `BashTool`，确认命令仍正常执行，且 Scheduler 的成功计数增加。

建议验证命令：

```bash
node --test test/execution-scheduler.test.js test/bash-tool.test.js test/run-subagent.test.js
npm test
```

当前完整测试中有一个与本期改造无关的既存失败：`docs/TUTORIAL_NEW.md` 引用了不存在的 `./architecture.html`。本期新增的调度器、Bash 与子 Agent 相关测试均通过。

## 9. 与 JD“超大规模并发治理”的关系

本期完成的是 JD 中“运行时争用治理”的最小可运行版本：限制本机执行并发，按会话/角色分配槽位，排队超时和取消可观测。

但以下能力尚未实现，不能混淆：

| 能力 | 本期状态 | 原因 |
|---|---|---|
| 页缓存复用 | 未实现 | 需要镜像层、内核页缓存及容器/microVM 运行时 |
| 内存回收 | 未实现 | 当前没有 cgroup、容器资源统计或 OOM 治理 |
| CPU/内存超卖 | 未实现 | 本期只管理执行槽位，不管理真实资源配额 |
| 强隔离 | 未实现 | `sh -c` 仍运行在宿主机权限内 |
| 跨节点调度 | 未实现 | Scheduler 是单进程内存队列 |

下一期可以保持 `ExecutionScheduler` 不变，新增 `DockerBackend` 替换 `_runProcess`：任务获得调度槽位后进入带 CPU/内存/PID/网络限制的容器。再后续可把 Scheduler 拆为控制面，把实际执行下沉到 Host Agent。

## 10. 关键结论

第一期的核心不是“多起几个 Shell 进程”，而是把执行从无约束的副作用，变成具有身份、状态、配额、取消和观测数据的任务：

```text
立即 spawn
  ↓
可排队、可限流、可取消、可观测的 Execution Job
```

在 Agent Runtime 中，模型的并发 Tool Call 仍可以保持并行语义；Scheduler 则负责决定哪些调用现在真的可以消耗执行资源。这种分层让后续替换执行环境、接入容器资源限制和扩展为分布式调度时，不需要改动 ReAct Loop、Provider 或 Registry 的核心协议。
