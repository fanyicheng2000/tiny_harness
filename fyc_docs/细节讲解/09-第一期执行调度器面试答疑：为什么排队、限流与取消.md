# 09｜第一期执行调度器面试答疑：为什么排队、限流与取消

> 本文只解释第一期 `ExecutionScheduler`：为什么要在本机 Shell 执行前增加队列、并发限制、排队超时和取消。重点是理解设计动机、并发语义，以及它和第二期 Docker 沙盒的关系。

---

## 0. 先用一句话定义第一期

第一期不是“为了让任务排队而排队”，而是在 Agent Runtime 和真实 OS 进程之间增加一个**准入控制器**：

```text
改造前：Agent 调 bash → 立刻 spawn 子进程

改造后：Agent 调 bash → 创建 Execution Job → Scheduler 判断当前是否允许启动
                                      ├── 允许：启动子进程
                                      ├── 暂时不允许：排队
                                      └── 等太久/主动取消：结束任务
```

它解决的核心问题是：**模型可以很快地产生很多工具调用，但宿主机的 CPU、内存、PID、文件描述符和 I/O 都是有限的。**

---

## 1. “同一个 Session 或 Worker 可以占满全部执行槽位”是什么意思？

### 1.1 先区分 Session、Worker、执行槽位

在本项目中：

```text
Session：一次主 Agent 任务的整体会话
Worker：一种子 Agent 角色，如 reviewer / tester
Thread：某个 Worker 的一次具体子任务实例
执行槽位：Scheduler 允许同时运行的真实 bash 任务名额
```

例如用户发起“检查并修复项目”：

```text
Session: fix-project-001
  ├── reviewer Thread A：读取代码、运行 grep / test
  ├── tester   Thread B：运行测试
  └── fixer    Thread C：修改文件、运行构建
```

主 Agent 或子 Agent 每次调用 `bash`，最终都可能变成一个 OS 进程：

```text
ToolCall(bash)
  → BashTool
  → sh -c "npm test"
  → npm 子进程
  → 测试进程及其继续创建的子进程
```

“执行槽位”不是 CPU 核本身，而是 Runtime 人为设置的**同时允许开始执行的任务数量**。例如：

```text
maxConcurrent = 4
```

含义是：整个 Node.js 进程最多同时有 4 个 Execution Job 处于 `RUNNING`；第 5 个先排队。

### 1.2 不加 Session / Worker 配额时会发生什么

假设全局上限为 4，主任务 `Session A` 的 Agent 一次产生 4 个并发 Bash 调用：

```text
Session A
  ├── bash: npm test
  ├── bash: npm run build
  ├── bash: find . -type f
  └── bash: grep -R "TODO" .

Session B
  └── bash: git status
```

如果只有全局 `maxConcurrent = 4`：

```text
A 的四个任务先拿到全部 4 个槽位
B 的 git status 即使很轻量，也必须等待
```

这就是“同一个 Session 可以占满全部执行槽位”。它并不表示同一个 Session 一定有恶意行为；也可能只是模型在同一轮 Function Calling 中并发请求了多个工具。

同理，某个 Worker 角色如果被多次委派，或多个 Thread 同时运行，也可能占满槽位：

```text
reviewer Worker
  ├── Thread 1 → bash
  ├── Thread 2 → bash
  ├── Thread 3 → bash
  └── Thread 4 → bash
```

因此第一期有三层约束：

```text
全局上限             maxConcurrent
单 Session 上限       maxPerSession
单 Worker 角色上限    maxPerAgent
```

例如：

```text
maxConcurrent = 4
maxPerSession = 2
maxPerAgent = 2
```

那么即使 `Session A` 或 `reviewer` 一口气提交很多任务，也最多各自同时运行 2 个；剩余槽位能让其他 Session / Agent 使用。

### 1.3 多个子 Agent 同时开命令进程，哪些资源可能耗尽？

会。准确说，不是“只要多开几个 `cmd` 就一定耗尽”，而是**无上限的并发进程及其子进程会争抢有限宿主机资源**。

| 资源 | 为什么会被消耗 | 例子 |
|---|---|---|
| CPU 时间 | 每个进程都要被操作系统调度 | 多个 `npm test` / `npm run build` 同时编译、跑测试 |
| 内存 | Node、编译器、测试框架、子进程都会分配内存 | 4 个构建任务同时运行，可能触发 swap 或 OOM |
| PID / 进程表 | Shell 命令可能继续 fork 子进程 | 测试 runner、watcher、递归脚本，极端时 fork bomb |
| 文件描述符 | 进程打开文件、pipe、socket、日志输出 | 并发 grep / test / git 读取大量文件 |
| 磁盘 I/O 与页缓存 | 多个任务同时扫描、编译、读取依赖 | `find`、`grep -R`、构建读取 `node_modules` |
| 网络连接 | 任务允许联网时会并发请求外部服务 | `npm install`、拉取依赖、调用 API |
| 磁盘空间 | 命令写构建产物、临时文件、日志 | build、coverage、缓存目录 |

第一期最直接控制的是**并发执行数量**，它并不直接限制 CPU 或内存；第三期才把 CPU / 内存规格纳入 Scheduler 的资源准入，第二期的 Docker 后端才引入 cgroup 层面的实际资源限制。

所以面试时要区分：

```text
第一期：用并发槽位降低资源争用概率，防止无限制 spawn。
第二期：用 Docker 对单个任务设置 CPU / 内存 / PID 等硬边界。
第三期：用声明式 CPU / 内存预算做资源准入和背压。
```

## 2. 排队、排队超时和取消有什么意义？主流吗？

### 2.1 为什么需要排队

排队的含义不是“系统慢”，而是当资源暂时不足时，**不让请求直接失控，也不直接丢弃合法任务**：

```text
任务到达
  ├── 当前有资源 → 立即运行
  └── 当前无资源 → 留在 PENDING 队列，等资源释放
```

如果没有队列，通常只剩两种选择：

1. **无限制执行**：所有命令直接 `spawn`，高并发时将压力转移给 OS；
2. **立即拒绝**：达到上限就报错，虽然安全，但用户体验差，很多本可稍后成功的任务被丢弃。

队列提供第三种方式：**有限等待**。这也是服务端线程池、连接池、消息队列、数据库连接池的常见思路。

### 2.2 为什么需要排队超时

只排队、不设置上限会产生“永远等待”的任务：

```text
任务 A 占满执行资源且卡住
任务 B、C、D 一直排队
Agent 不知道任务已经不可能及时完成
```

排队超时定义了服务承诺边界：

```text
排队超过 maxQueueWaitMs
  → 不再启动
  → 状态为 QUEUE_TIMEOUT
  → 返回明确错误给模型
```

它有三个作用：

- **保护队列长度和内存**：避免长期积压任务无限堆积；
- **保证时效性**：等待太久的旧任务即使最终执行，结果也可能已经无意义；
- **给 Agent 可行动的反馈**：模型可以减少并发、换轻量方案、等待后重试，或向用户说明资源繁忙。

要区分两个超时：

```text
排队超时：还没有开始运行，等资源太久
命令超时：已经开始运行，但命令本身运行太久
```

前者是 Scheduler 的容量治理，后者是 Backend / BashTool 的进程生命周期治理。

### 2.3 为什么需要取消

取消主要处理两种场景：

```text
场景 1：任务仍在 PENDING
        用户/上层 Agent 已改变计划，不需要再运行
        → 直接从队列结束，不占任何执行资源

场景 2：任务已经 RUNNING
        用户停止任务、上层任务超时、需要主动止损
        → AbortSignal 通知 Backend
        → 本地后端 SIGKILL；Docker 后端 kill / rm 容器
```

没有取消能力时，一旦模型发起长命令，系统只能被动等它超时；而上层任务已经结束、用户已经退出或计划已经改变时，这些进程仍会白白消耗资源。

### 2.4 这是主流实现方式吗？

**设计原则是主流的；当前实现是教学/单进程版本。**

主流系统通常都有以下概念：

| 通用概念 | 常见系统中的叫法 |
|---|---|
| 并发限制 | worker pool、thread pool、semaphore、concurrency limiter |
| 排队 | work queue、message queue、pending queue |
| 排队超时 | queue deadline、TTL、admission timeout |
| 运行超时 | execution deadline、request timeout |
| 取消 | cancellation token、AbortSignal、context cancellation |
| 配额 | tenant quota、per-user limit、per-queue limit |
| 资源准入 | resource admission、scheduler predicate、bin packing |

例如：

- Web 服务会用连接池、线程池、请求队列；
- Kubernetes Scheduler 会根据 CPU / 内存 request 判断 Pod 能否放入节点；
- 消息队列消费者会控制并发和 ack deadline；
- Go 使用 `context.Context` 传播取消，Node.js 使用 `AbortSignal`。

但本项目当前不是生产级调度器：队列和状态都在单个 Node.js 进程内，没有持久化、分布式 Leader、跨节点调度、重试语义、死信队列或租户治理。面试时应说：

> 我参考了通用的 admission control、deadline 和 cancellation 模式，在单进程 Agent Runtime 中实现了教学版 ExecutionScheduler；它验证了接口和状态机，生产环境还需要持久化队列与分布式 Worker。

## 3. 为什么要改造成“可治理的单进程调度系统”？还能并发吗？

### 3.1 “单进程调度系统”不是“单任务串行执行”

这里的“单进程”指：Scheduler 的队列、计数器、状态机运行在**当前 Node.js 进程内存中**。

它不等于：

```text
一次只能运行一个子 Agent
一次只能执行一条命令
```

实际仍然支持并发：

```text
主 Agent
  ├── Worker A → bash A
  ├── Worker B → bash B
  ├── Worker C → bash C
  └── Worker D → bash D

Scheduler(maxConcurrent = 4)
  → A、B、C、D 同时 RUNNING
```

若 `maxConcurrent = 2`：

```text
A、B → RUNNING
C、D → PENDING
A 或 B 完成后 → C / D 被调度启动
```

因此它是**受控并发**，不是取消并发。

### 3.2 为什么不继续使用 `Promise.all` 直接 spawn

Engine 的 `Promise.all` 仍然保留：它表达的是“同一轮 Tool Call 之间没有数据依赖，可以并行提交”。

但“并行提交”不应该等于“无条件并行执行”：

```text
Promise.all 的职责：并发提交多个独立任务
Scheduler 的职责：根据系统资源决定其中哪些现在真正运行
```

这和 Web 服务中的模式相同：客户端可同时发起 100 个请求，但服务器不应该同步创建 100 个昂贵 Worker。

### 3.3 单进程版本的价值

在引入 Docker、多机、任务数据库之前，单进程 Scheduler 仍然很有价值：

1. **先明确任务模型**：Job ID、状态机、排队/运行超时、取消、资源归属等语义先稳定下来；
2. **防止本机演示直接失控**：Agent 一次并发调多个 Shell 时，不把压力无上限传给宿主机；
3. **低复杂度验证策略**：可以先验证 `maxPerSession`、`maxPerAgent`、优先级、资源预算是否合理；
4. **为分布式演进保留接口**：未来只需将内存 `pending` 队列替换为 Redis / 数据库 / MQ，并把 `run()` 送往 Host Agent；上层 Tool / Agent 接口无需改变。

### 3.4 单进程版本的限制

它也有明确局限：

```text
Node 进程重启 → 内存队列丢失
多 Node 实例 → 各自只看见自己的队列和资源
无法跨机器分配任务
无法保证全局唯一调度
```

所以“单进程调度器”是正确的第一步，而不是最终平台形态。

## 4. 第一期开关和后续容器技术是什么关系？

可以把三期理解成三个相互补充的层：

```text
第一期：Admission Control（要不要现在开始）
第二期：Isolation（开始后在哪里、安全边界是什么）
第三期：Resource-aware Scheduling（按什么资源规格开始、是否复用环境）
```

### 4.1 第一期开关无法替代容器

第一期的 `maxConcurrent = 4` 只能说明：

```text
最多同时运行 4 个任务
```

它不能保证：

```text
每个任务最多 512MB 内存
每个任务最多 1 CPU
任务不能联网
任务不能访问宿主机文件
任务不能创建超过 128 个进程
```

因为这些是 OS / 容器运行时的隔离与资源限制，需要 Docker、cgroup、namespace 等机制。

### 4.2 Docker 无法替代第一期调度

反过来，如果只引入 Docker、每个任务都 `docker run`，但没有 Scheduler：

```text
Agent 一次发起 100 个 Tool Call
  → 同时启动 100 个容器
  → 宿主机 Docker daemon、镜像层、CPU、内存仍可能被打满
```

Docker 给每个任务边界，但不能自动替你决定“当前是否应该再启动一个任务”。因此仍需要队列、配额、排队超时、取消和资源准入。

### 4.3 最终组合关系

```text
Agent 并发 Tool Call
  → 第一/三期 Scheduler
      - 任务是否准入
      - 资源是否足够
      - 谁优先
  → 第二期 Docker Backend
      - 在什么隔离环境运行
      - 单任务资源硬上限
  → 第三期 ContainerPool
      - 是否复用已启动环境
      - 异常实例如何销毁替换
```

一句面试表达：

> Scheduler 解决系统层面的“何时启动、谁先启动”；Docker 解决任务层面的“启动后如何隔离”；两者是正交且互补的，不能互相替代。

## 5. ExecutionScheduler 带来了什么？改造前是什么样？

### 5.1 改造前：直接执行模型

第一期前的 Bash 工具逻辑大致是：

```js
async execute({ command }) {
  return new Promise((resolve, reject) => {
    const child = spawn('sh', ['-c', command]);
    // 收集输出、命令超时后 SIGKILL、按退出码返回
  });
}
```

特点：

```text
收到调用 → 立即 spawn
```

已有的能力包括：

- Shell 命令运行超时；
- `SIGKILL` 终止超时进程；
- stdout / stderr 收集和输出截断；
- Registry 将异常统一转换为 ToolResult；
- Engine 同一轮以 `Promise.all` 并发执行工具。

但缺少：

```text
任务 ID / 状态机
全局并发限制
按 Session / Worker 的公平配额
排队与排队超时
外部取消运行任务
排队时长、运行时长等执行指标
```

### 5.2 改造后：Execution Job 模型

改造后每一次 Bash 调用先构造 Job：

```text
Execution Job
  id
  sessionId / agentId
  status
  submittedAt / startedAt / finishedAt
  queueWaitMs / runMs
  AbortController
  priority / resources（第三期）
```

执行链路变成：

```text
BashTool.execute
  → Scheduler.submit
  → PENDING
  → 检查全局、Session、Agent、资源预算
  → RUNNING
  → Backend.execute
  → SUCCEEDED / FAILED / CANCELLED
```

### 5.3 相比之前具体好在哪里

| 维度 | 改造前 | 有 ExecutionScheduler 后 |
|---|---|---|
| 并发行为 | 每个 Tool Call 直接 spawn | 有最大并发槽位，受控并发 |
| Session / Worker 公平性 | 先来的任务可能占满资源 | 单 Session / Agent 配额限制独占 |
| 过载处理 | OS 被动承担压力 | 不够资源则排队，等待过久超时 |
| 任务取消 | 只能等命令超时 | 可主动取消 PENDING / RUNNING Job |
| 状态可见性 | 只有最终 ToolResult | 可看到 PENDING、RUNNING、终态及耗时 |
| 观测 | 只看到工具调用 Span | 有排队、启动、结束 Trace Event |
| 后端扩展 | BashTool 内部绑定 `spawn` | Scheduler 可调度 local / Docker / 未来远程 Backend |
| 资源治理 | 只控制命令自身超时 | 第三期可按 CPU / 内存规格准入 |

最核心的提升是：

```text
改造前：工具调用 = 立刻执行的副作用
改造后：工具调用 = 可识别、可排队、可取消、可观测、可准入的 Execution Job
```

这也是它能自然演进到 Docker 沙盒、资源准入、容器池和未来分布式 Host Agent 的原因。

## 6. 面试时可以如何回答

### Q1：为什么需要限制 Agent 工具并发？

> 模型可以在同一轮一次性返回多个 Function Call，多个子 Agent 也能并发执行。如果 Bash 调用直接 spawn，构建、测试、递归检索等命令会同时竞争 CPU、内存、PID、I/O 和文件描述符。第一期在 Runtime 中加入 Scheduler，将工具调用转成 Execution Job，通过全局、Session、Agent 三层并发配额实现受控并发，避免单个任务或 Worker 抢占全部执行资源。

### Q2：排队和超时的区别是什么？

> 排队超时是任务尚未开始、等待资源过久，属于容量治理；命令超时是任务已经运行但执行过久，属于进程生命周期治理。前者避免队列无限堆积，后者避免单条命令卡死。两者都需要，不能只保留其中一个。

### Q3：加 Scheduler 后是不是子 Agent 不能并发了？

> 不是。Agent 层仍通过 `Promise.all` 并发提交无依赖工具调用；Scheduler 只在资源有限时延迟部分 Job。比如全局上限 4 时，4 个子 Agent 命令仍可并发；第 5 个开始排队。这是受控并发，不是串行化。

### Q4：为什么有 Docker 还要 Scheduler？

> Docker 解决单任务的隔离和资源硬上限，Scheduler 解决系统整体的准入和公平性。没有 Scheduler，100 个容器仍可能同时启动并压垮宿主机；没有 Docker，Scheduler 也无法阻止单个进程越权访问或超额占用资源。二者分别处理“何时运行”和“在哪里运行”。

### Q5：这个实现是生产级的吗？

> 不是，它是单进程的教学/原型实现：状态和队列都在内存中，进程重启会丢失，不能跨节点调度。但它已经把 Job 模型、状态机、取消、deadline、配额和 Backend 抽象稳定下来；生产化可以将内存队列替换为持久化任务存储或 MQ，再由多台 Host Agent 消费执行。
