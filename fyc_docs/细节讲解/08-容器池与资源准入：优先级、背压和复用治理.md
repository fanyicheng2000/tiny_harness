# 08｜容器池与资源准入：优先级、背压和复用治理

## 1. 第三期要解决的问题

前两期分别解决了两件事：

```text
第一期：命令会不会无限制并发？
        → 队列、执行槽位、Session / Agent 配额、取消

第二期：命令在哪运行、如何隔离？
        → Local / Docker Backend、网络/文件系统/能力/资源限制
```

但 Docker 后端仍是“一次任务 = 一次 `docker run`”：每次都创建容器、初始化文件系统、启动进程，频繁短任务会带来冷启动开销。同时第一期的调度只按“任务个数”限制，不知道任务声明了多少 CPU / 内存；一个小型 `ls` 与一次重型构建占用同样一个槽位，无法表达资源竞争。

第三期将执行治理继续推进为：

```text
任务声明资源规格 + 优先级
  → Scheduler 资源准入 / 背压
  → Docker 容器池借用已有容器
  → docker exec 执行
  → 清理现场后归还 / 销毁
```

本期目标是实现单进程、单机版的资源调度和容器复用基础，而不是生产级 Kubernetes 调度器。

## 2. 总体架构

```text
Agent ToolCall(bash)
  └── { command, priority?, resources? }
          │
          ▼
BashTool
  └── Scheduler.submit(...)
          │
          ▼
ExecutionScheduler
  ├── 执行槽位：maxConcurrent
  ├── 归属配额：maxPerSession / maxPerAgent
  ├── 资源预算：totalCpuMillis / totalMemoryMb
  ├── 优先级队列：priority 越大越先调度
  └── 状态机 / 排队超时 / 取消 / Trace
          │
          ▼
DockerBackend(poolSize > 0)
  └── ContainerPool（按 workDir 分池）
       ├── idle container → 直接借用
       ├── 未达池上限 → 创建新容器
       └── 已达池上限 → 等待归还
          │
          ▼
docker exec <container> sh -c <command>
          │
          ▼
健康 → reset → 归还
异常/取消 → kill → destroy → 补充实例给等待者
```

其中 Scheduler 仍决定**任务何时可运行**；Backend / Pool 决定**可运行后如何拿到执行环境**。这条边界保证以后换成远程 Host Agent 或 microVM 时，Agent、Registry、Scheduler 协议不必重写。

## 3. 资源规格与资源准入

### 3.1 Tool Call 增加声明字段

`bash` 的输入 Schema 在原有 `command` 之外新增：

```js
{
  command: 'npm test',
  priority: 10,
  resources: {
    cpuMillis: 2000,
    memoryMb: 2048,
  },
}
```

| 字段 | 含义 | 默认值 |
|---|---|---:|
| `priority` | 整数；值越大越优先 | `0` |
| `resources.cpuMillis` | 声明 CPU，1000m = 1 核 | `1000` |
| `resources.memoryMb` | 声明内存预算 | `512` |

这里的资源规格是 Runtime 的**调度契约**。它告诉 Scheduler：启动该任务前需要从当前可用预算中扣除多少资源。

### 3.2 两层资源限制

第三期有两类不同的资源概念：

```text
Scheduler 声明预算：决定能否开始任务
Docker cgroup 限制：决定容器实际最多能使用多少资源
```

举例：

```text
Scheduler 总预算：4 CPU / 4096 MB
任务 A 声明：2 CPU / 2048 MB
任务 B 声明：2 CPU / 2048 MB
任务 C 声明：1 CPU / 512 MB

A + B 可以同时运行；C 必须等待其中一个结束。
```

Scheduler 维护 `allocated.cpuMillis` 和 `allocated.memoryMb`。每个任务启动时扣除、结束时归还；调度条件为：

```text
已分配 CPU + 任务 CPU ≤ CPU 总预算
AND
已分配内存 + 任务内存 ≤ 内存总预算
```

Docker 非池化模式下，任务规格会传入 `docker run`，覆盖 Backend 默认的 `--cpus` / `--memory`。这使“调度声明”与“容器实际限制”保持一致。

> 容器池模式中，池容器在创建时已获得固定 cgroup 限制，`docker exec` 无法为每条命令重新设置 CPU/内存。因此池适合资源规格相同的一类任务；不同规格应配置不同 Backend / Pool，或在下一期把 Pool Key 扩展为 `image + resourceProfile`。

### 3.3 立即拒绝与背压等待

- 若单个任务声明资源超过总预算，例如总内存 4096MB、任务声明 8192MB：任务直接进入 `RESOURCE_REJECTED`，不进入队列。
- 若单任务规格合法但当前剩余预算不足：保留 `PENDING`，等待运行任务释放资源。
- 若等待超过 `maxQueueWaitMs`：进入 `QUEUE_TIMEOUT`。

这三种情况不同：

```text
RESOURCE_REJECTED：永远不可能满足，配置/任务规格有问题
PENDING：暂时没有足够资源，正常背压
QUEUE_TIMEOUT：等待太久，容量或优先级策略需要调整
```

`getSnapshot()` 增加：

```js
{
  limits: { totalCpuMillis, totalMemoryMb, ... },
  allocated: { cpuMillis, memoryMb },
  metrics: { resourceRejected, ... }
}
```

因而可区分“队列慢”究竟来自并发槽位、Session/Agent 配额还是资源预算。

## 4. 优先级：在可运行任务中选择谁

第一期按提交顺序扫描可运行任务。第三期先过滤通过所有准入条件的任务，再排序：

```js
priority 降序 → submittedAt 升序
```

含义：

- 高优任务优先获得刚释放的资源；
- 相同优先级保持 FIFO；
- 如果队头任务因资源不够不能运行，后面较小但满足预算的任务可以先运行，避免队头阻塞。

示例：

```text
当前可用：1 CPU / 512MB

队列：
A：priority=0，2 CPU / 1024MB（不满足）
B：priority=5，1 CPU / 512MB（满足）

→ B 先运行，A 继续等待。
```

当前策略没有 aging（随排队时间提高优先级）。因此大量持续到来的高优任务理论上可能让低优任务等待到超时；这是一种有意保留的、可观察的策略边界，后续可加入老化或配额保留机制。

## 5. ContainerPool：容器如何复用

新增 `src/execution/container-pool.js`，它只依赖一个很小的 runtime 接口：

```js
runtime.create({ image })   // 创建常驻容器
runtime.reset(container)    // 归还前清理现场
runtime.destroy(container)  // 销毁异常容器
```

通过这个接口，池化逻辑不依赖真实 Docker；单元测试可以用 fake runtime 覆盖借用、归还和异常替换，而不需要 Docker daemon。

### 5.1 状态与借用规则

```text
idle 队列有实例
  → 取出并复用

idle 为空且 created < poolSize
  → 创建新实例

idle 为空且 created == poolSize
  → 当前请求成为 waiter，等待归还
```

正常归还：

```text
任务完成
  → runtime.reset(container)
  → 有 waiter：直接交给 waiter
  → 无 waiter：放回 idle
```

异常归还：

```text
命令超时 / 取消 / docker exec 失败
  → unhealthy
  → destroy(container)
  → 有 waiter：创建 replacement 后交给 waiter
```

池快照包括：`created`、`idle`、`borrowed`、`reused`、`released`、`destroyed`、`waiters`，可用于判断是否真的减少了冷启动、是否频繁因任务失败销毁实例。

### 5.2 Docker 池实现

DockerBackend 设置 `poolSize > 0` 时，按 `workDir` 建立独立 Pool：不同项目工作区不共用容器，避免工作目录挂载混淆。

池实例使用后台常驻命令创建：

```bash
docker run -d ... sh -c 'while true; do sleep 3600; done'
```

执行任务时改为：

```bash
docker exec <container-id> sh -c '<command>'
```

正常结束后通过 `docker exec` 执行 reset。当前 reset 实现仅清理 `/workspace` 顶层的 `*.tmp` 文件，并保留 `.tiny-harness`：这是一个保守示例，避免误删用户项目源代码。

**重要限制：**当前工作区是用户真实项目目录的 `rw` 挂载，因此不可能在归还时清空整个 `/workspace`；否则会删除 Agent 正常产生的源码改动。生产级池化通常为每个任务创建独立的 overlay / worktree / snapshot，归还时回滚该任务层，再把基础环境复位。

## 6. 配置

新增环境变量：

| 环境变量 | 默认值 | 作用 |
|---|---:|---|
| `TINY_HARNESS_TOTAL_CPU_MILLIS` | `4000` | Scheduler CPU 总预算 |
| `TINY_HARNESS_TOTAL_MEMORY_MB` | `4096` | Scheduler 内存总预算 |
| `TINY_HARNESS_DOCKER_POOL_SIZE` | `0` | 每工作区 Docker 容器池上限；0 表示关闭池化 |

示例：

```bash
TINY_HARNESS_EXECUTION_BACKEND=docker \
TINY_HARNESS_DOCKER_IMAGE=node:22-alpine \
TINY_HARNESS_DOCKER_POOL_SIZE=2 \
TINY_HARNESS_TOTAL_CPU_MILLIS=4000 \
TINY_HARNESS_TOTAL_MEMORY_MB=4096 \
node src/index.js --provider openai --prompt "运行测试并修复失败"
```

建议初期保持 `TINY_HARNESS_DOCKER_POOL_SIZE=0`，先验证 Docker 单任务模式。只有当任务镜像、隔离策略、工作区清理规则明确后再启用池化。

## 7. 状态机、Trace 与故障处理

新增状态：

```text
RESOURCE_REJECTED
```

状态机现在为：

```text
submit
  ├── 单任务规格超过总预算 → RESOURCE_REJECTED
  └── PENDING
       ├── 排队超时 → QUEUE_TIMEOUT
       ├── 取消 → CANCELLED
       └── 配额 + 资源准入通过 → RUNNING
            ├── 成功 → SUCCEEDED
            ├── 执行异常 → FAILED
            └── 取消 → CANCELLED
```

Trace 中的 `execution.queued / started / finished` 事件增加 `priority` 和 `resources` 属性。这样问题排查时可以回答：

- 任务是否因为资源预算而没启动？
- 运行时占用了什么资源规格？
- 高优任务是否长期挤压低优任务？
- 某个 Agent / Session 是否持续提交重型任务？

## 8. 测试覆盖

新增和扩展测试：

### Scheduler

- 高优任务在资源释放后优先于低优任务执行；
- 两个 1000m CPU 任务在 1500m 总预算下不会并发；
- 任务结束后已分配资源归零；
- 单任务规格超过集群容量时立即进入 `RESOURCE_REJECTED`；
- 第一、二期全局并发、Session 配额、排队超时、取消测试保持通过。

### ContainerPool

- 健康实例归还时先 reset、再次 acquire 会复用同一容器；
- 异常实例归还时销毁，等待者获得新建 replacement。

验证命令：

```bash
node --test test/execution-scheduler.test.js \
  test/container-pool.test.js \
  test/execution-backend.test.js \
  test/bash-tool.test.js
```

真实 Docker 池需要 Docker daemon；当前自动化验证采用 fake runtime 覆盖池状态机，未在本环境执行实际 `docker run` / `docker exec`。

## 9. 与 JD 的关系和诚实边界

第三期更接近“运行时争用治理”和“密度优化”的起点：

| JD 方向 | 本期能力 | 边界 |
|---|---|---|
| 运行时争用治理 | 槽位 + Session/Agent + CPU/内存预算准入 | 单机、声明式预算 |
| 成本优化 | 容器池接口与复用指标 | 未量化真实冷启动/成本收益 |
| 资源隔离 | Docker cgroup 限制 | Pool 中规格固定，不能按 exec 动态改 cgroup |
| 内存回收 | 任务结束释放调度预算、销毁异常容器 | 非宿主机 page cache / 内核回收 |
| 超卖 | 未实现 | 没有真实利用率采样和 OOM 驱逐 |
| 页缓存复用 | 未直接实现 | 复用常驻容器可能减少启动路径，但不应称为页缓存优化 |

简历或面试应表述为：

> 在 Agent Runtime 中实现单机执行调度：按任务声明的 CPU/内存规格进行准入和优先级调度，并设计 Docker 容器池的借用、复位、异常销毁及替换机制，降低重复创建执行环境的开销；未将其表述为生产级超卖或页缓存复用系统。

## 10. 下一步

要进入更接近 JD 的生产级阶段，还需要：

```text
1. 将 Pool Key 扩展为 image + resourceProfile + networkPolicy；
2. 为每个任务使用 overlay / snapshot / git worktree，安全完成归还前清理；
3. 采集宿主机真实 CPU / 内存 / PSI / OOM 指标，做资源水位准入；
4. 引入优先级 aging、公平队列、租户配额和限流；
5. Scheduler / Task Store 服务化，Host Agent 执行并上报心跳；
6. 接入 containerd、gVisor 或 microVM，增强隔离边界。
```

第三期的核心改变是：系统不再只把“并发”当成一个数字，而是把每次 Agent 执行当作带有优先级、资源规格、生命周期和可复用环境的调度任务。
